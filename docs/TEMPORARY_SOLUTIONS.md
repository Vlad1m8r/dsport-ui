# TEMPORARY SOLUTIONS (MVP)

## 1) DEV fallback initData (`user id = 12345`)
- **Что это:** локальный fallback Telegram `initData` для разработки вне Telegram.
- **Почему временно:** нужен только для DEV-стенда и ускорения проверки флоу.
- **Что позже:** перейти на полноценный Telegram initData в окружениях, где доступен WebApp-контекст; fallback оставить только как строго dev-only механизм.

## 2) Planned values defaults (`plannedReps=0`, `plannedDurationSeconds=null`)
- **Что это:** временные дефолты для новых плановых подходов в редакторе шаблонов.
- **Почему временно:** упрощают создание draft и совместимость текущего UI с контрактом.
- **Что позже:** более строгие стартовые значения и UX-валидация с типизированными пресетами по типу упражнения.

## 3) `Exercise.type` управляет UI, строгая серверная валидация — позже
- **Что это:** фронтенд показывает поля подхода по `exercise.type` (`REPS_WEIGHT` vs `TIME`).
- **Почему временно:** текущий этап MVP фокусируется на UX-потоке и базовой валидации.
- **Что позже:** усилить серверные ограничения по типу упражнения и синхронизировать ошибки/коды с UI.

## 4) Нет виртуализации в ExercisePicker (до ~500 упражнений)
- **Что это:** каталог рендерится без windowing/virtualization.
- **Почему временно:** текущий размер справочника позволяет работать без заметной деградации.
- **Что позже:** добавить виртуализацию списка при росте каталога и замерах производительности в Telegram WebView.

## 5) Нет optimistic updates для критичных списков
- **Что это:** после мутаций используется invalidate/refetch вместо ручного optimistic merge.
- **Почему временно:** это снижает риск дублей и конфликтов на этапе стабилизации.
- **Что позже:** точечно внедрять optimistic updates там, где это даёт заметный UX-выигрыш, с обязательной дедупликацией по `id`.
